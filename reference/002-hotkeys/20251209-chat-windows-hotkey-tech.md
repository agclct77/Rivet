## 1. AutoHotkey (AHK) 技術詳解

AutoHotkey 是一個強大的 Windows 自動化腳本語言，其核心能力遠超出了簡單的「按鍵映射」。以下深入分析其技術細節與注意事項。

### 1.1 技術架構：為什麼它如此強大？

* **底層掛鉤 (Keyboard & Mouse Hooks)**：
  * AHK 使用 Win32 API `SetWindowsHookEx` 來安裝 `WH_KEYBOARD_LL` 和 `WH_MOUSE_LL` 掛鉤。
  * 這讓它能在按鍵訊息進入任何應用程式的「訊息佇列 (Message Queue)」之前，就先攔截到該訊息。
  * **$ 修飾符 (Hook 強制 + 防自觸發)**：在腳本中寫 `a::Send b` 會有風險（按下 a -> 送出 b），如果腳本裡還有 `b::Send c` 可能引發連鎖反應。使用 `$`(例如`$a::`) 會強制熱鍵走鍵盤 Hook，並抑制腳本「自己送出的按鍵」再次觸發同一熱鍵。
* **輸入模擬模式 (Send Modes)**：
  * `SendInput` (最推薦)：幾乎無延遲，可靠性最高；合成輸入直接插入系統輸入佇列，通常能壓過手動輸入的時序，但不會特意「緩衝」實體鍵盤事件。
  * `SendEvent`：模擬按鍵按下的延遲，速度較慢，但對某些老舊應用程式（對輸入速度敏感）相容性較佳。
  * `SendPlay`：早期用於繞過某些遊戲的反作弊保護，但在較新 Windows 環境或受保護的全螢幕應用中成功率較低。

### 1.2 進階應用場景

* **上下文感知 (Context Sensitivity)**：
  * AHK 可以動態偵測當前視窗。
  * `#IfWinActive ahk_exe chrome.exe`：可以讓熱鍵 **只在** Chrome 瀏覽器中生效，而不影響其他程式。這是解決快捷鍵衝突的一個重要手段。
* **GUI 介面開發**：
  * AHK 內建強大的 GUI 指令，可以創建複雜的設定視窗、儀表板或浮動工具列 (Floating Toolbar)。
  * 它可以監聽視窗訊息 (`OnMessage`)，甚至呼叫 DLL (`DllCall`) 來使用 Windows API 的深層功能。

### 1.3 開發與安全注意事項

* **安全機制**：務必設置「緊急停止鍵 (`ExitApp`)」與「暫停鍵 (`Pause`)」，防止死迴圈（如無限點擊滑鼠）導致無法操作電腦。
* **版本差異**：
  * **v1 (Classic)**：語法較混亂（命令式），網路上 90% 的舊腳本屬於此類。
  * **v2 (Modern)**：語法嚴謹（類 JavaScript/Python），物件導向支援佳，**強烈建議新專案使用**，但不相容 v1。
* **反作弊風險**：AHK 的行為模式（攔截輸入、模擬操作）與外掛特徵完全一致。在帶有反作弊系統（VAC, Vanguard, BattlEye）的遊戲中執行 AHK（即使只是用來調音量），極高機率會導致 **永久封號**。

## 2. Windows 快捷鍵處理優先級 (Hierarchy)

在 Windows 中，快捷鍵衝突並不會跳出對話框問你「要選哪個程式」，而是依據一套殘酷的技術優先級來決定。處理流程是一個「過濾鏈 (Chain)」。

| 層級               | 名稱                                                   | 技術特徵                          | 衝突處理機制                                            | 代表性 API           |
| :----------------- | :----------------------------------------------------- | :-------------------------------- | :------------------------------------------------------ | :------------------- |
| **1 (最高)** | **系統底層保留 (System Reserved)**               | 核心層級，應用程式無法覆蓋。      | 系統強制攔截，應用程式收不到訊號。                      | 無 (Kernel)          |
| **2**        | **底層鍵盤掛鉤 (Low-Level Hooks)**               | 監聽所有訊號，決定攔截或放行。    | **後安裝先執行 (Last Installed, First Called)**。 | `SetWindowsHookEx` |
| **3**        | **註冊的全域快捷鍵 (Registered Global Hotkeys)** | 向系統「登記」特定組合鍵。        | **先搶先贏 (First Come, First Served)**。         | `RegisterHotKey`   |
| **4 (最低)** | **應用程式層級 (App-Specific Accelerator)**      | 僅當視窗擁有焦點 (Focus) 時觸發。 | 不同視窗互不衝突。                                      | `WM_KEYDOWN`       |

### 2.1 詳細競爭規則

* **Hooks (第 2 層)**：如果你開啟了兩個都使用 Hook 的軟體（例如 AHK 和 鍵盤映射工具），**最後啟動**的那一個會排在隊列的最前面，擁有優先決定權。
* **Registered Hotkeys (第 3 層)**：如果你開啟了兩個都想註冊 `Ctrl+Space` 的軟體，**先啟動**的那一個會成功，後面的會收到「註冊失敗」錯誤。
* **診斷困難**：Windows **沒有** 提供一個原生的介面來查看「目前哪個程式佔用了 Ctrl+C」。這使得排查非常困難，通常只能靠「排除法」或使用 AHK 強制 Hook 來覆蓋。

## 3. 業界專案快捷鍵實作案例分析

本章透過分析知名軟體的快捷鍵實作機制，探討不同需求下的技術選擇與權衡。*(註：層級定義請參閱第 2 章)*

### 3.1 Ueli / PowerToys Run (快速啟動器)

* **功能需求**：一鍵喚醒 (如 `Alt+Space`)，低延遲，需在任何視窗之上運作。
* **技術策略**：**第 3 層 (Registered Global Hotkeys)**。
* **分析**：
  * Ueli (Electron) 和 PowerToys Run (C#/.NET) 都傾向使用標準的 `RegisterHotKey` API。
  * **優點**：實作簡單，系統資源消耗極低（由 OS 負責派送訊息，不需要程式自己一直輪詢）。
  * **缺點**：如果快捷鍵被更底層的程式（如 AHK）攔截，或者被先啟動的其他程式註冊，功能會註冊失敗（呼叫會直接回報失敗）；PowerToys 會在設定介面提示「快捷鍵註冊失敗」。

### 3.2 Discord / OBS (遊戲與通訊工具)

* **功能需求**：**Push-to-Talk (按鍵發話)**。需要在全螢幕遊戲（獨佔模式）中依然能偵測到按鍵，且不能觸發遊戲的反作弊機制。
* **技術策略**：**第 2 層 (Low-Level Hooks)** 或 **Raw Input**。
* **分析**：
  * 標準的註冊熱鍵在某些全螢幕遊戲中可能會失效，或者會有明顯延遲。
  * Discord 使用底層 Hook 來確保即便視窗未對焦也能收到訊號。
  * **權衡**：這類軟體通常需要「以系統管理員身分執行」，否則當遊戲本身是以管理員權限執行時，Discord 的 Hook 層級會低於遊戲，導致按鍵失效（這是使用者常問「為什麼我在遊戲裡說話沒反應」的主因）。

### 3.3 VS Code (複雜生產力工具)

* **功能需求**：海量快捷鍵、連擊鍵 (Chords, 如 `Ctrl+K` 後接 `Ctrl+V`)、上下文感知 (`When` 子句)。
* **技術策略**：**第 4 層 (Application-Specific)** 的極致優化。
* **分析**：
  * VS Code 並不依賴全域 Hook（除了極少數 OS 整合功能）。它的強大在於內部的 **Keybinding Service**。
  * **架構**：它攔截網頁層級的 `keydown` 事件，然後透過一套複雜的規則引擎 (Rules Engine) 來比對當前的 `context`（例如：現在焦點在編輯區？還是在側邊欄？有選取文字嗎？）。
  * **啟示**：如果你的軟體只在視窗內運作，不要去碰底層 Hook，應該學習 VS Code 建立一套靈活的內部事件分發系統。

### 3.4 Microsoft PowerToys (Keyboard Manager)

* **功能需求**：**按鍵重映射 (Remap)**。例如把鍵盤上的 A 鍵變成 B 鍵。
* **技術策略**：**第 2 層 (Low-Level Keyboard Hooks)**。
* **分析**：
  * 與 PowerToys Run 不同，Keyboard Manager 必須改變按鍵的「行為」，而不僅僅是讀取。
  * 它必須在訊號傳遞給應用程式**之前**攔截它，修改 `vkCode` (虛擬鍵碼)，然後再送回系統鏈中。這正是 `SetWindowsHookEx` 的典型應用。
  * 這也解釋了為什麼 PowerToys 有時會跟遊戲或其他鍵盤軟體衝突，因為大家都在搶同一個 Hook 鏈的優先權。

### 3.5 華碩智慧輸入法 / QTranslate (輔助工具)

* **功能需求**：**被動觸發**。使用者不是為了呼叫軟體而按鍵，而是為了操作文字（選取），軟體要「猜」出使用者的意圖（查字典）。
* **技術策略**：**第 2 層 Hook (偵測雙擊)** + **剪貼簿代理 (Ctrl+C)**。
* **分析**：
  * 這是 UX 設計引導技術選擇的經典案例。為了達到「選取即查」的流暢體驗，開發者選擇了最暴力但也最通用的路徑。
  * 它避開了複雜的 UI Automation，選擇了模擬使用者行為 (`Ctrl+C`)，雖然技術上不優雅，但產品體驗上卻是相容性最高的解法。

### 3.6 Snipaste / ShareX (截圖工具)

* **功能需求**：接管系統特殊鍵 `PrintScreen`。
* **技術策略**：**第 3 層 (RegisterHotKey)** + **登錄檔監控**。
* **分析**：
  * 在 Windows 10/11 之後，微軟試圖將 `PrintScreen` 收歸國有（綁定到「剪取工具」）。
  * 第三方工具如 ShareX 必須在啟動時嘗試註冊此鍵。如果失敗（被系統佔用），它們有時會引導使用者去 Windows 設定中關閉「使用 Print Screen 鍵開啟剪取工具」的選項，或者使用 Hook 強行攔截。

## 4. UI Automation 的替代方案：如何「取得選取文字」？

在開發類似「華碩智慧輸入法」或「劃詞翻譯」工具時，最困難的一步往往不是熱鍵，而是**「如何取得使用者現在選取的文字」**。Windows 並沒有提供一個簡單的全域 API 來做這件事。以下是幾種常見的技術路徑：

### 4.1 方案 A：剪貼簿代理 (Clipboard Injection) - **最通用、最暴力**

這是華碩智慧輸入法、以及大多數翻譯軟體（如 QTranslate）採用的方法。

* **原理**：
  1. 偵測到熱鍵 (如雙擊 Ctrl) 觸發。
  2. **備份** 當前剪貼簿內容（為了不覆蓋使用者原本複製的東西）。
  3. 程式在背景模擬發送 **`Ctrl + C`**。
  4. 等待極短時間 (Sleep 50-100ms) 讓系統完成複製。
  5. 讀取剪貼簿文字。
  6. **還原** 原本備份的剪貼簿內容。
* **優點**：相容性極高，只要該程式支援 Ctrl+C 就能運作（瀏覽器、Word、記事本皆可）。
* **缺點**：
  * 會破壞使用者的剪貼簿歷史（雖然有還原，但剪貼簿管理軟體可能會記錄到中間那次操作）。
  * 有微小延遲。
  * 若目標程式禁止複製（如某些 DRM 保護的 PDF），此法無效。

### 4.2 方案 B：UI Automation (UIA) & Accessibility API - **正規但複雜**

* **原理**：使用微軟提供的 `UI Automation` 或舊版的 `IAccessible` 介面。這些 API 原本是為了螢幕閱讀器（給視障人士用）設計的。
* **流程**：
  1. 取得當前焦點視窗的 Handle。
  2. 透過 UIA 查詢該視窗內的 `TextPattern` 或 `ValuePattern`。
  3. 請求 `GetSelection()` 方法。
* **優點**：乾淨、不干擾剪貼簿、不需模擬按鍵。
* **缺點**：
  * **極度複雜**：程式碼量大，且處理樹狀結構很慢。
  * **相容性差**：很多非標準 UI 的程式（如 Chrome 早期版本、或是用 Qt/Java Swing 寫的程式）對 UIA 支援不完整，可能抓不到選取範圍。

### 4.3 方案 C：OCR (光學字元辨識) - **終極手段**

* **原理**：不嘗試去「讀」文字代碼，而是直接「看」螢幕。
  1. 取得當前選取區域的座標（這本身也很難），或者讓使用者自己框選一個區域。
  2. 對該區域進行螢幕截圖。
  3. 使用 OCR 引擎 (如 Tesseract, Windows 10/11 內建 OCR API) 辨識圖片中的文字。
* **優點**：**無敵**。連圖片裡的字、防複製網頁、甚至遠端桌面裡的字都能抓出來。
* **缺點**：
  * 效能開銷大（截圖+辨識）。
  * 準確度非 100%，可能會認錯字。

### 4.4 方案 D：Hook TextOut / DrawText (GDI Hooking) - **古老黑魔法**

* **原理**：直接 Hook 系統底層負責「畫字」的 GDI 函數 (`TextOutA`, `TextOutW`)。
* **現狀**：**已幾乎被淘汰**。現代瀏覽器和應用程式多使用 DirectWrite 或 GPU 加速渲染，根本不走傳統 GDI，因此抓不到。
